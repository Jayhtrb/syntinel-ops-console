# SynTinel Operations Console

A dark-first, single-page redesign of the JTOCC operational dashboard, rebranded
as **SynTinel** for Synchrony (using the supplied Synchrony logo + brand gold),
combined with the **Verint WFO (Tableau)** workforce view, and topped with a
**portfolio health hierarchy** (RAG portfolios → impacted services → incident
trends) built from the supplied portfolio-mapping workbook. Same business
purpose, same telemetry, rebuilt as a responsive React application optimised for
**1366×768** and **1920×1080** at 100% browser zoom.

```bash
npm install          # dependencies (React 19, Vite, MUI 9, Recharts 3, Lucide)
npm run dev          # http://localhost:5199
npm run build        # tsc --noEmit && vite build
npm run preview      # serve the production build
npm run smoke        # data + render smoke test (100+ assertions)
```

---

## Portfolio health hierarchy

The default view is the **portfolio health map**: five portfolios/departments —
Customer Service, Notesviewer, Collections, Fraud, Risk — each carrying a
**red / amber / green** verdict. Clicking a red or amber portfolio drills down to
its **impacted services**, grouped by capability with a brief impact description,
and an **incident trend** (14 days) for the selected portfolio or service.

- Mapping: `src/data/portfolio/mapping.ts` — parsed from
  `Workstation_Middleware_Portfolio_Mapping_With_Descriptions.xlsx`
  (176 services · 20 capabilities · 5 portfolios).
- Deterministic demo health + incident series: `src/data/portfolio/health.ts`.
- The original operational telemetry is preserved as the **Telemetry** view,
  reached from the header **Health / Telemetry** switcher.

## Plug-and-play data sources

`src/data/sources.ts` is the single seam to production tools. Each domain is
mapped to a tool in `sourceConfig`:

| Domain | Production tool |
| --- | --- |
| `service-health` | New Relic |
| `incidents` | ServiceNow / PagerDuty |
| `call-telemetry` | Avaya CMS |
| `workforce` | Verint WFO |
| `reports` | Tableau |

To connect a tool: set `sourceConfig.domain` to its kind, add the endpoint +
auth under `sourceConfig.tools`, and implement the fetch in the adapter registry
(`adapterFor`). Stub adapters fail loudly with wiring instructions until the
tool is connected, so nothing silently serves mock data. UI components never
change when a source is swapped.

### Captured vs synthesised data

Everything the screenshots show is reproduced exactly. `src/data/mock/` documents
its own provenance at the top of each file:

* **Captured** — the ten client rows and their queue/active/SLA figures; all ten
  MW service rows (error count, throughput, error rate) and the four capability
  labels with their `0.00` badges; AWS Singapore 298 and Azure Singapore 206
  sessions; region and cloud tab labels; the five workstation login totals and
  `Active Users: 3`.
* **Synthesised** — the other six regions' session counts, every peak/average,
  day-over-day deltas, the trend waveforms, and the `previous window` block used
  for delta indicators. Series follow the captured shapes (twin daily peaks,
  overnight troughs) and are generated by a **seeded PRNG**, so a refresh always
  produces identical data.
* **Ambiguity kept honest** — the source `ERROR COUNT` column is internally
  inconsistent (e.g. `2.054` against 1,106 calls with a `0.000` rate). It is
  reproduced verbatim, labelled as captured, and the error *rate* is treated as
  authoritative. Credit Line and OTP capability tabs are shown as `idle` because
  the capture shows their badges but no service rows.
* Two source fragments were folded rather than duplicated: the second
  "Overall System Call Status" row (1 / 68 / 83.9) is a later sample of the same
  metric, and the unlabelled `CNB_ALL / Cathay_DC_All / Cheapo_CMB  0 0`
  fragment duplicates client rows already present.

## 2. Design direction

**Control-room instrumentation, not a card grid.**

* **Type** — Saira (condensed grotesque) for display and panel titles, IBM Plex
  Sans for prose, IBM Plex Mono for every numeral. All three are self-hosted via
  `@fontsource`, so there is no runtime font CDN and numbers stay column-aligned.
* **Colour** — one cold accent (`#5AD1FF` ice) over a five-step near-black ramp,
  with four signal colours: nominal teal, watch steel, warning amber, critical
  red. Colour is never the only carrier of meaning.
* **Surface** — panels are chamfered at the top-right, hairline-bordered and
  lifted with an inset highlight; the page carries a masked instrument grid, two
  radial glows and a 3.5% grain to stop large dark fields banding.
* **Motion** — restrained: a 380 ms staggered rise on first paint, a travelling
  scan line on the panel being refreshed, a 2.4 s pulse on the live indicator,
  420 ms meter fills. Everything collapses under
  `prefers-reduced-motion: reduce`.
* **Composition** — one page, one scroll column. No permanent left nav (there is
  one page) and no right intelligence panel (it would steal width the table needs
  at 1366 px). Panels are chosen so the operational table and login summary are
  visible above the fold at 768 px height and the trend chart joins them at
  1080 px.

## 3. Structure

```
src/
  App.tsx                     composition, filters, scope routing
  types/dashboard.ts          the data contract shared by both layers
  lib/                        formatting + status thresholds (pure)
  data/
    dashboardRepository.ts    the single seam to telemetry (swap this for HTTP)
    scopes.ts                 application scopes and date ranges
    kpis.ts                   per-scope KPI derivation
    insights.ts               attention signals + operational notices
    mock/                     captured seeds, deterministic series, scenarios
  hooks/                      snapshot loading, wall clock
  components/
    layout/                   TopBar, FilterBar, SectionPanel, SkipLink
    common/                   StatusPill, DeltaChip, MeterBar, Sparkline, atoms
    feedback/                 notices, error/empty/not-collected, skeletons
    dashboard/                8 panels
  theme/                      tokens -> MUI theme + injected CSS variables
```

**Presentation never touches mock data.** Components receive a
`DashboardSnapshot`; every threshold lives in `lib/status.ts`, every derived
number in `data/`. Swapping the mock repository for a live API is a one-file
change, and `npm run smoke` asserts the contract either way.

### Panels

1. **Compact header** — identity, overall verdict, data window, refresh, QA state
   selector.
2. **Scope bar** — application, date window, and (Citrix only) cloud + region.
3. **Operational notices** — data-derived banners, ranked, critical pinned first.
4. **System status strip** — overall queue SLA with target notch, queue depth,
   active calls, services, error rate, active users.
5. **Attention strip** — "what needs a person now" as tappable filters that drive
   the table.
6. **KPI row** — five scope-aware tiles with verdict, movement and sparkline.
7. **Operational performance table** — client queues / service throughput /
   region sessions, sortable, with SLA meters and inline reasons.
8. **Application logins** — totals, share, idle call-outs, Today / 7-day toggle.
9. **Operational trend** — one chart, four views (call load, service level,
   workstation activity, concurrent sessions).

### Prioritising the operator's questions

* **SLA deterioration** — SLA sorts first by default; meters carry a target notch;
  `< 95%` is *below target*, `< 85%` is a *breach*. Both are stated in words.
* **Unusual call volume** — queue depth is thresholded (`watch ≥ 1`,
  `warning ≥ 5`, `critical ≥ 15`) and clipped to a second axis so it cannot hide
  behind the active-call curve.
* **Inactive applications** — a client with no traffic, or a workstation app with
  zero logins, is labelled `idle` instead of showing a bare zero, and is named in
  the notice.
* **Clients needing attention** — `attention` chips filter the table in one click,
  and each flagged row carries the reason inline (`SLA 80.8% · 4.2pt below the
  85% floor · 1 call waiting`).
* **Workforce deterioration** — the Verint scope flags adherence below target,
  occupancy into burnout territory, forecast misses and falling IVR containment;
  the roster panel lists the teams to review in severity order.

## 4. States

Loading, empty, error, warning and critical are implemented as first-class
surfaces, and every one is addressable for review:

| State | Inspect it | Behaviour |
| --- | --- | --- |
| Live | `/` | Verdicts derived from the captured data: one critical queue, two below target, eight with no live traffic |
| Loading | `/?state=loading` | Layout-matched skeletons; the request never settles |
| Empty | `/?state=empty` | Empty tables, `—` KPIs, no sparklines, "nothing to evaluate" attention strip, informational notice |
| Error | `/?state=error` | Gateway 503 copy, retry, no stale figures (a frozen SLA reading is worse than none) |
| Warning | `/?state=warning` | Five queues under target, elevated service errors, **no** critical notice |
| Critical | `/?state=critical` | Three breached queues, error-rate spike, drained region, critical notices |

Refresh keeps the previous snapshot visible (`refreshing`) rather than flashing
empty, and a failed reload keeps the last good snapshot with an error banner.

Other deep links: `?app=citrix&cloud=azure&region=azure-mumbai`, `?range=14d`.

## 5. Accessibility

* Status is icon + written label + colour, never colour alone.
* Semantic tables with captions, `scope="col"`, `aria-sort` on sortable headers,
  and a visible focus ring (`2px` ice, 2px offset) on every control.
* The trend chart is `role="img"` with a spoken summary of the series rendered in
  the panel; the same numbers are in the KPI row and the table.
* Critical notices use `role="alert"`, warnings and info use `role="status"`.
* Skip link, 4.5:1 minimum text contrast, `prefers-reduced-motion` support.

## 6. Verification

`npm run smoke` loads the real modules through Vite's SSR pipeline and renders
them with `react-dom/server`, so TSX, the data layer and every panel are
exercised. It asserts, among 68 checks, that the captured figures survive
transformation (1 queued / 66 active / 83.9% SLA / 80.8% PAYPAL_ALL / 298 AWS /
206 Azure / 219 Customer Service), that the worst SLA sorts first, that each
scenario produces its intended state, and that the empty and error surfaces
render.

The visual review was done with headless Chrome screenshots at 1366×768,
1366×900, 1920×1080 and full-page height, in every scope and every state.

## 7. Deliberately out of scope

These are **not implemented**; they are recorded here as future opportunities
only, so nobody mistakes their absence for an oversight:

* **AI predictions** — no forecasting, anomaly scoring or "likely to breach"
  ranking. The trend chart is descriptive; a forecast band would need a model,
  a backtest and an owner before it belongs on an operations wall.
* **Verint quality scoring** — first-contact resolution, CSAT/NPS and evaluation
  quality scores are deliberately not merged in yet; the combined console covers
  adherence, AHT, occupancy, forecast accuracy and IVR containment only.
* **Role-based access** — the console is single-persona. Real deployment needs
  SSO, queue-level entitlement and a masked view for non-operational roles.
* **Audit logging** — no record of who viewed or acted on a signal. Any workflow
  that notifies an owner must be auditable first.
* **Export / reporting** — no CSV, PDF or scheduled mail. If added, it must
  respect the same scoping and date filters and be generated server-side.
* **No persistence** — filters and selections are in-memory, so a reload returns
  to the default scope. Deep links are the interim answer.
